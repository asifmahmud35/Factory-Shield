## Story

As an Approver, I want to manually escalate an incident when I cannot action it in time,
and I want the system to auto-escalate when the SLA is breached, so that critical incidents
always receive timely attention.

## Acceptance Criteria

1. `POST /api/v1/incidents/{id}/escalate` accepts `{ reason }` from an authenticated Approver;
   reason must be ≥ 10 characters or the API returns 400.
2. On escalate: `Incident.EscalationLevel` increments by 1 and an `Escalation` row is written
   with `EscalationType = "MANUAL"`, `Reason`, `EscalatedById`, `EscalatedAt`.
3. Escalating a terminal incident (Resolved / Closed / Rejected) returns 400.
4. `SlaCheckJob` auto-escalates on SLA breach: increments `EscalationLevel`, writes an
   `Escalation` row with `EscalationType = "SLA_AUTO"` and `EscalatedById = null`.
5. Auto-escalation fires exactly once per breach (guarded by the same BREACHED notification
   check, preventing duplicate escalation across multiple job runs).
6. Approver queue rows with SLA elapsed ≥ 80% show a red `!` indicator on the incident reference.
7. The Approver incident detail has an "⬆ Escalate" button; clicking it reveals a reason textarea
   + "Confirm Escalation" button; success shows a green confirmation message.

## Dev Notes

**Auto-escalation guard:** `AutoEscalateAsync` checks `_notifications.ExistsAsync(..., SLA_BREACHED)`
before writing the escalation. Since `FireOnceAsync(SlaBreached)` writes the notification in the
same job run (before `AutoEscalateAsync` returns), the guard correctly prevents a second auto-
escalation if the job fires again before the clock's `StoppedAt` is persisted.

**EscalatedById nullable:** `SLA_AUTO` escalations have no human actor — `EscalatedById` is null.
EF handles this as a nullable column (no FK constraint on `EscalatedById`).

**`!` indicator:** Computed client-side from `slaStartedAt + slaTargetMinutes` (same data the
countdown badge uses). No extra API call needed. Updates when the queue refreshes.
