## Story

As a Resolver, I want to mark an incident as Resolved once all corrective actions have been created, so the incident officially exits the active investigation pipeline.

## Acceptance Criteria

1. Given I am authenticated as Resolver, when I call `POST /api/v1/incidents/{id}/resolve`, then the incident's status transitions from `IN_PROGRESS` to `RESOLVED` and the API returns HTTP 200.
2. Given no corrective actions exist for the incident, when I call resolve, then the API returns HTTP 400 with `"At least one corrective action must exist before resolving an incident."`.
3. Given the incident does not exist, then the API returns HTTP 404.
4. Given the incident is not in `IN_PROGRESS` status, the state machine throws `InvalidOperationException` and the API returns HTTP 400.
5. Given the investigation workspace is open, the "Mark Resolved" button is **disabled** when 0 CAPA actions exist.
6. Given ≥ 1 CAPA action exists, the "Mark Resolved" button becomes enabled. On click, the API is called and the user is navigated to `/resolver/assigned` (incident no longer appears in the list).

## Dev Notes

**State machine:** `IN_PROGRESS → RESOLVED` was already in the adjacency map from the initial implementation. No changes to `IIncidentStateMachine` or `IncidentStateMachine` needed.

**CAPA guard is application-layer only:** The "≥ 1 CAPA" rule is enforced in the command handler, not the state machine. The state machine stays clean — it only enforces status graph edges.

**No new migration:** Incident status is stored as a string column — no schema change needed when adding a new valid status value that was already anticipated.

**`@Output` pattern:** `CapaTrackerComponent` emits the count (not a boolean) so the workspace can show future UI like "3 / 5 complete" if needed.
