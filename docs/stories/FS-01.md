## Story

As an authenticated Reporter, I want to submit a basic incident report (category, severity, short description) so that the incident enters the system with a unique reference and is ready for an Approver to review.

## Acceptance Criteria

1. Given I'm authenticated, when I `POST /api/v1/incidents` with `category` and `short_description`, then the API creates the incident and returns HTTP 201 with `incident_id` and `incident_reference` (format `INC-{YYYY}-{NNNN}`, unique per year).
2. Given `severity` is omitted in the request, then it defaults to Low (stored as `4`, per architecture.md §3.2 severity mapping).
3. Given `category` or `short_description` is missing, then the API returns HTTP 400 with field-level validation errors, and no incident is created.
4. Given an incident is created, then `status = SUBMITTED` (via the state machine, not set directly) and `reporter_id` is set to the authenticated user's ID.
5. Given the Angular report form is filled correctly and submitted, then a confirmation screen displays the returned `incident_reference`.
6. Given the Angular report form is submitted with required fields missing, then inline validation errors show before any API call is made.

## Dev Notes

**State machine scope:** Build only the simplified MVP enum here, not the full 16-state Governance Spec machine (`DRAFT/SUBMITTED_LOCAL/TRIAGED/.../INVESTIGATION/RCA_REVIEW/...`). The full granular machine is documented in architecture.md §3 but explicitly deferred per §11 — building it now would burn time on states this MVP never reaches (INVESTIGATION onward only fires for severity ≥ L2 with a full approval pipeline, which isn't in scope). Still route every status write through `IIncidentStateMachine`, never set `Incident.Status` directly — that discipline matters even at MVP scope so FS-05/FS-06/FS-10 plug in cleanly later.

**Department:** Keep as a plain string field on `Incident`, not a separate `Department` entity/table — architecture.md §4.1 defines a full `departments` table, but that's more structure than this MVP needs. Document this simplification, don't silently diverge.

**Authorization:** Any authenticated user can create an incident for MVP (not gated to a `REPORTER`-only role check) — in practice anyone can report an incident regardless of their primary role. Full RBAC enforcement per architecture.md §6 gets tightened story-by-story as Approver/Resolver endpoints are built.
