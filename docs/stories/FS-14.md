## Scope Decision

The full FS-14 in SPRINT_PLANNING.md includes a Hangfire recurring job that fires staged
notifications (50 % / 80 % / breach) and a `notifications` table. That heavy infrastructure
(new NuGet dependency + background worker + dashboard) was **split out** into a follow-up
slice **FS-14b**. This story delivers the SLA data model and the visible countdown UI —
enough for Approvers and Resolvers to see time pressure — with **zero new dependencies**.

**Delivered here:** SLA clocks tracked per stage, started/stopped across the incident
lifecycle, and a colour-coded countdown badge in the Approver queue and Resolver assigned list.
**Deferred to FS-14b:** automatic notification firing (Hangfire), `notifications` table.

## Story

As an Approver / Resolver, I want to see an SLA countdown on each incident so that I can
prioritise work by how close each item is to breaching its service-level target.

## Acceptance Criteria

1. When an incident is created, a `TRIAGE` SLA clock starts, with `TargetMinutes` resolved from severity (Critical 60 → Low 1440).
2. When an Approver approves an incident, the running `TRIAGE` clock is stopped (`StoppedAt` set) and an `ASSIGNMENT` clock starts.
3. `GET /api/v1/approver/queue` and `GET /api/v1/resolver/assigned` include `slaStartedAt`, `slaTargetMinutes`, `slaStage` for the active clock (null when none running).
4. The Approver queue and Resolver assigned list render a colour-coded SLA badge: green < 50 %, amber 50–80 %, red 80–100 %, solid-red "BREACHED" ≥ 100 %.
5. The badge shows remaining time (e.g. `3h 12m left`) and ticks down once per minute without a page reload.
6. Incidents with no active clock (e.g. the Reporter's own list) show a neutral `—` and never crash.

## Dev Notes

**Shared DbContext, single transaction:** repositories are all scoped over the same
`AppDbContext`. `CreateIncidentCommandHandler` adds both the incident and its clock, then one
`SaveChangesAsync` commits atomically — no explicit transaction needed.

**Client-side breach evaluation:** the countdown badge computes stage/breach in the browser
from `startedAt + targetMinutes`. No server round-trip and no background job — that is exactly
why this slice needs no Hangfire. FS-14b will add server-side firing for notifications.

**SLA budget table (`SlaPolicy`):** minutes by stage × severity —
TRIAGE 60/240/480/1440, ASSIGNMENT 120/480/960/2880, RESOLUTION 480/1440/2880/5760.

**Stage as string:** `SlaClock.Stage` is a string, not an enum, so future pipeline stages
(INVESTIGATION, RCA_REVIEW…) don't force an enum migration.
