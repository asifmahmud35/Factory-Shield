# Story FS-05: Approver Approve/Reject Incident

**Status:** Done
**Epic source:** Epic 2 (Approver Workflow) — US-4, US-5
**Depends on:** FS-04 (Done)
**Blocks:** FS-06 (Reassign), FS-07 (Resolver Assigned)

---

## Story

As an Approver viewing an incident in the queue, I want to approve it (assign to a Resolver and move it forward) or reject it (soft reject: allow Reporter dispute, or hard reject: final denial), so incidents move through the approval stage efficiently.

## Acceptance Criteria

1. Given I'm authenticated as Approver and viewing a SUBMITTED incident detail, when I click "Approve" and select a Resolver, then the API `POST /api/v1/incidents/{id}/approve` accepts the resolver ID and transitions the incident to `TRIAGED` status, storing the resolver assignment.
2. Given I approve an incident, then the incident is visible in that Resolver's assigned list (FS-07) and no longer in the Approver queue (FS-04).
3. Given I click "Soft Reject" with a reason, then the incident transitions to `REJECTED` but the Reporter can dispute it within a window (stored but not enforced in MVP — AC is just that transition happens).
4. Given I click "Hard Reject" with a reason ≥10 characters, then the incident transitions to `REJECTED` and cannot be disputed — final decision.
4b. Given I try to reject with reason <10 chars, then the API returns HTTP 400 with validation error.
5. Given the Angular incident detail view, then "Approve" button shows a Resolver dropdown, and "Soft Reject" / "Hard Reject" buttons show a reason textarea with character counter.
6. Given an incident is approved/rejected, then the incident's status badge on the Approver queue (FS-04) updates in real-time or on page refresh to reflect the new state (Approved → not in queue, Rejected → shows rejected status).

## Dev Notes

**State transitions:** Approver's approve moves SUBMITTED → TRIAGED (not directly to ASSIGNED — assignment happens separately in the full system). For MVP, treat TRIAGED as "assigned to a Resolver" functionally (even though canonically TRIAGED is pre-assignment in the governance model). Document this simplification.

**Resolver selection:** The Approve button needs a dropdown of available Resolvers (filtered from users with RESOLVER role). Fetch this via a new API or hardcode the 3 demo users for MVP.

**Soft vs. Hard reject:** Soft allows Reporter to dispute (future feature, FS-11), Hard is final. Both transition to REJECTED status; the distinction is stored in metadata (not critical for MVP, just the state transition matters).

**Real-time queue update:** After approve/reject, the queue page should reflect the change. Simplest: just navigate away and back to `/approver/queue` — no WebSocket needed for MVP.
